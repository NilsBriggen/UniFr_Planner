# Optional accounts and explicit synchronization

Guest planning continues in IndexedDB without an account. Settings offers username/password registration, login, and recovery in DE/FR/EN. No email or external identity provider is involved. Never reuse MyUnifr credentials or upload transcripts.

Signing in, creating an account, or recovering an account copies all valid local plans into **new** account plans. Existing server plans and local plans are never replaced. Repeated sign-ins intentionally make additional copies. If import fails, settings reports that the account is signed in but the copy failed; the local plan remains available for retry.

Synchronization is explicit: edit the current local plan, then choose **Sync current plan** in settings. The browser session remembers only account-scoped local/server IDs and revisions in sessionStorage. It stores no session token or recovery code. With unavailable or cleared sessionStorage, the next sync creates a new server copy. Refreshing server plans does not advance the local revision. Copying a server plan to the device creates a new local plan and selects it.

Each server revision covers the complete schema-v1 plan, all scenarios, courses, unavailable periods, and requirement evidence. PostgreSQL serializes mutations on the account row. A write with a stale revision returns HTTP 409 with the current server plan and a separately persisted conflict copy. The local plan is then linked to its conflict copy. Both versions remain listed for explicit selection. No automatic conflict merge occurs.

Account export is a validated schema-v1 JSON archive with username, export timestamp, and revisioned plan snapshots. Password/session/recovery hashes are excluded. Individual snapshots are compatible with guest JSON import. Account deletion requires the current password, deletes that account's server plans and sessions, and leaves local device copies and other accounts intact.

## Security and deployment

- Passwords exclusively use Argon2id, 64 MiB, three iterations, parallelism four, with individual random salts. Recovery is one 256-bit random code, SHA-256 hashed at rest, returned once on registration/recovery. Recovery consumes the old code, generates a replacement, resets the password, and revokes every existing session atomically. Lost passwords and lost codes cannot be recovered by email.
- Sessions are random 256-bit tokens, stored only as SHA-256 hashes. The `__Host-unifr_session` cookie is always Secure, HttpOnly, SameSite=Strict, Path=/, with no Domain and a 30-day absolute expiry. Successful login rotates the current browser session. Logout revokes its token. A maximum of 20 sessions per account bounds growth; the oldest is revoked when exceeded.
- Deploy behind HTTPS. Secure cookies are never weakened for deployment. Chromium's trustworthy loopback exception permits local browser development. Other browsers may require local HTTPS.
- Set `UNIFR_ACCOUNT_ORIGINS` to an exact JSON list, for example `["https://planner.example.org"]`. Mutations require an allowed Origin and reject `Sec-Fetch-Site: cross-site`. No wildcard CORS is enabled. Compose forwards this setting. The default only permits the documented local frontend origins.
- Persistent atomic fixed-window counters apply to registration, login, recovery and deletion: 10 attempts per canonical username, 30 per client address, and 300 globally per 15-minute window. Failed attempts consume the budget; responses use a conservative 900-second Retry-After. Fixed windows can allow two budgets around a boundary. Counters are pruned on the next attempt after expiry; they contain hashes, not plaintext usernames or IPs. Do not enable arbitrary forwarded-IP trust; configure ASGI proxy trust only for the actual reverse proxy. The global ceiling is deliberately conservative and can temporarily deny legitimate activity during abuse.
- Request bodies are bounded before parsing, including chunked bodies: 4 KiB for auth, 20 MB for plan operations. Every snapshot must fit the guest 5 MB formatted JSON limit. Accounts are limited to 100 plans and 20 MB serialized plan data. If a conflict cannot fit, the server rejects the write without modifying either version; the local snapshot remains available. Export before deleting/recreating an account when its quota is full. There is no per-plan server deletion in this delivery.
- Private responses, including errors, carry no-store/no-cache. Validation errors are deliberately redacted because FastAPI's default can echo secret input. Login and recovery use uniform invalid-credential messages. No credential logging is implemented. Operators must also avoid request-body logging at proxies and observability layers.
- Run `alembic upgrade head` before starting the API. Migration `0003_accounts` creates four tables, foreign keys/cascade relations, uniqueness and owner indexes. PostgreSQL is required for production concurrency guarantees; SQLite is used only for isolated UI demonstrations and fast HTTP tests. Deletion from existing external backups follows the operator's backup-retention policy; the API does not rewrite historical backups. Server snapshots are private by authorization, not end-to-end encrypted.

## Contract and verification

`node --experimental-strip-types scripts/generate_plan_schema.mjs` regenerates the structural server schema from the guest Zod schema. Cross-field invariants and JavaScript/Python regex/trim differences are checked in `account_models.py`; the browser parity test detects schema drift. `npm run api:generate` regenerates OpenAPI and the typed client.

`UNIFR_TEST_DATABASE_URL=... .venv/bin/pytest` enables disposable-schema PostgreSQL migration and simultaneous-write/recovery/rate-limit controls. `npm run test:e2e -- accounts.spec.ts --workers=1` runs DE/FR/EN desktop/phone account flows with Axe and real browser cookies against disposable demo databases. Browser artifacts contain only synthetic test credentials; never use real accounts in these tests.
